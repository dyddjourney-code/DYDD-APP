# Sandbox Circles commerce contract (billing owner)

Billing integrates with existing `journey_circle_plans` (`id,user_id,status,plan.format`) and `dydd_circle_memberships` (`circle_id,user_id,status,accepted_at`). No replacement Circle tables. Billing migration: `20261104220000_circle_billing_rules.sql`.

Use `getCircleBillingState(ownerId,circleId,format)` from `lib/commerce/circle-billing.ts` AFTER exact Circle authorization. It returns `phase` (`active|transition|read_only|unpaid`), `canCreate`, `canEnroll`, `canOperate`, `canRead`, `paidThrough`, `transitionEndsAt`, `personalActive`, `couples`. `requireCircleBillingAction(ownerId,circleId,format,action)` throws on prohibited create/enroll/operate; read always preserves history. For creation use `getAccountCircleBillingState(userId)` (leadership only); saved Couple drafts may be purchased but must not operate until that exact persistent Circle is paid. Transition allows existing work and transfer, NOT creation/new participants/invites. Thirty days after paid period end is read-only. Active renewal restores rights without altering records. Personal prerequisite remains separate; personal expiry never grants more leadership time. Participants still require their own personal access.

SQL service-only RPC `dydd_circle_billing_state(p_owner uuid,p_circle uuid,p_format text)` returns same fields; operational database functions can call it inside their own transaction (service role only). `dydd_circle_require_billing(p_owner,p_circle,p_format,p_action)` enforces `create|enroll|operate|read`. No billing function grants Circle ownership or participant/private-data access.

Couples: service-only persistent binding records payer + Circle ID and original intended partner email; reserve via `dydd_test_claim_couple(p_user,p_circle,p_owner_email)` before checkout. Payer can never buy a second Couple Circle even after deletion/archive; this binding has no cascading Circle FK. Expired checkout can retry same Circle only. Couple format and intended partner are locked once claimed; deleting/recreating is blocked by the permanent binding. Other party must be same explicitly intended partner; no global spouse data access. Operations must enforce two seats (organizer + one) and normal accepted membership identity.

Qualifying leadership count uses distinct current accepted paid personal participants, excludes all Circle owners themselves, personal free grants/trials/ended/refunded access. Earliest accepted current active membership attributes one leader; DC3 paid $5 qualifies. Leadership estimates are upcoming renewal only; existing period is not repriced. Couples memberships do NOT credit leadership. DC3 applies to Personal only via server-selected fixed product-restricted TEST coupon, never client-picked coupon.

No production/live payments/emails. APIs remain authenticated same-origin sandbox TEST paths. UI can read `GET /api/commerce/circles?circleId=...` and existing purchase-options, including billing state/upcoming amount.
