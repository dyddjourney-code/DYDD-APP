# Permanent personal beta access — 2026-10-28

## Learner flow
Normal signup is unchanged. Create an account, verify its email, open Base Camp → Purchases → Redeem beta access code. No card/payment. A successful redemption persists lifetime personal all-access on that exact authenticated account; reload/login does not depend on free-beta mode. Codes have no expiration and can only be claimed once. A repeat submission by the same owner succeeds safely. Already entitled accounts do not consume additional codes.

## Durable authorization contract
`dydd_personal_access` is the authoritative account-bound entitlement: `personal_all_access`, granted time, source invitation. There is **no expiration column, consumption counter, payment dependency or beta-end date**. This is a commercial grant, never assessment evidence, course completion or owner/admin authority. Account deletion removes its access; invitation history cannot be reassigned or recycled: deleting an account clears its code owner reference but retains redeemed_at as a permanently consumed tombstone.

`hasLifetimePersonalAccess(userId)` reads that permanent grant; `hasIncludedPersonalAccess(userId)` combines it with the temporary free-beta commercial policy. Future paid-launch code must call the permanent-aware helper for personal tool/report/course commercial gates, keeping ownership and all existing assessment/prerequisite checks separate. Do not replace this with `isFreeBeta()` or a badge/UI check.

Current real paid gates integrated: FruitLife entitlement eligibility, legacy paid session creation, no consumption of a paid one-shot when lifetime entitled, FruitLife checkout redirect before any Stripe access, DesignPD generation commercial gate and assessment UI. Existing completed DesignPD report/course access remains; DesignID/report readiness, lesson order and course completion checks are unchanged. Current nonlegacy FruitLife/Journey/DesignID/Spiritual Gifts commercial paths are already included for signed-in learners, with no additional payment gate to override. Future commerce for these must use the helper. This release does not implement a future paid catalog or unlimited services not yet built.

Personal all-access **does not grant paid Circle seats, access for other people, organizer/admin power, invitations, report sharing, observer identity, assessment results or bypass scoring/privacy/prerequisites**. Existing Circle ownership, membership and invitation restrictions are intentionally untouched. No paid Circle seat fulfillment is introduced; a future paid-seat system must remain separate. No beta invitation emails, payment calls or participant sends are performed by code redemption.

## Security and concurrency
128-bit cryptographically random codes, canonical `DYDD` plus32uppercase hex; spaces/hyphens/case normalized. Only SHA256 hashes are stored; plaintext exists solely in private owner deliverables outside Git. No code logs/URLs/analytics. Verified authenticated account is resolved server-side, never supplied by client. Server-only RPC independently checks `auth.users.email_confirmed_at`.

Additive migration creates three RLS-enabled tables. Anon/authenticated have no table access or RPC EXECUTE. Redemption RPC is SECURITY INVOKER, empty search_path, service-role-only. A narrow SECURITY DEFINER boolean verifier lives in the non-exposed `dydd_private` schema, checks confirmed/not-deleted auth identity, has an auth.uid cross-account guard, empty search_path, and service-role-only EXECUTE/USAGE. This avoids broad auth.users SELECT privileges. Transaction locks a per-account rate row then invitation row, checks ownership, inserts entitlement and marks redemption together. Twelve attempts per15minutes per verified account (including malformed guesses), durable across instances; high entropy prevents practical distributed guessing. Account lock serializes parallel claims for multiple codes; row lock prevents two accounts claiming one code. Invalid and already-used-by-someone-else share one message. Same-origin JSON POST; cross-site rejected. No service key in browser.

## Operational rules
Apply additive migration independently; never reset/merge databases. Securely back up existing schema/entitlement baseline first. Issue production codes separately from sandbox and QA. Do not consume owner codes for testing. Clean disposable QA entitlements before their code rows/users. Preserve code history for actual claims. Only delete real accounts on an explicit account-deletion request; code tombstones remain used. Paid launch must retain the table, helper and contracts above.

Private evidence: checkout `tmp/permanent-beta/RELEASE.md`; owner plaintext/invitation files are workspace `outputs/dydd-permanent-beta-2026-10-28/`, not tracked. No invitations sent. Browser proof is Chromium emulation, not physical iOS/Safari; report/PDF/email-provider generation is not exercised by redemption QA.
